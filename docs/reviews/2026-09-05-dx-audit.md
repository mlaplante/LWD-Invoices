## Findings ranked by severity

### HIGH

**H1. `npx tsc --noEmit` fails on current `main` — CI's type-check gate is red right now**
- Severity: High
- Evidence: running `npx tsc --noEmit` (fresh `npm install`, `package-lock.json`-pinned deps, matching CI's `npm ci`) produces:
  ```
  src/app/api/webhooks/resend/route.ts(58,15): error TS2352: Conversion of type 'undefined' to type 'ResendPayload' may be a mistake...
  src/server/services/stripe.ts(6,34): error TS2322: Type '"2026-07-29.dahlia"' is not assignable to type '"2026-08-26.dahlia"'.
  ```
  `src/server/services/stripe.ts:6` hardcodes `apiVersion: "2026-07-29.dahlia"` in `new Stripe(secretKey, { apiVersion: "2026-07-29.dahlia" })`, but the installed `stripe@22.6.0` (exactly what `package-lock.json` pins) now types `LatestApiVersion` as `"2026-08-26.dahlia"`. `.github/workflows/ci.yml`'s `check` job runs exactly `npx tsc --noEmit` as a **blocking** step.
- Why it matters: either CI is not actually red on `main` right now (in which case branch protection / required-checks may not be enforcing this job — worth confirming on GitHub) or every PR is currently failing CI for a reason unrelated to the PR's own change, which is a severe "why is my unrelated PR failing" DX trap. `next.config.ts:49`'s `typescript.ignoreBuildErrors: true` means `next build` locally will **not** surface this — a contributor following `CONTRIBUTING.md`'s documented workflow (test → coverage → build, no `tsc`) will ship it clean and only find out from CI, or not at all if they never watch CI status.
- Fix: pin the Stripe API version via `Stripe.LatestApiVersion` type instead of a literal string (or update the literal to `"2026-08-26.dahlia"` and add a regression test/CI step that fails loudly on the next Stripe bump). Also fix the `ResendPayload` cast at `src/app/api/webhooks/resend/route.ts:58` (use `as unknown as ResendPayload` if the cast is intentional, or narrow the type). Add `"typecheck": "tsc --noEmit"` to `package.json` scripts (see M-series below) so this class of break is caught before push, not just in CI.

**H2. Local pre-commit secret scan is hardcoded to an Apple-Silicon Homebrew path and not auto-wired on fresh clones**
- Severity: High
- Evidence: `githooks/pre-commit`:
  ```
  #!/usr/bin/env bash
  /opt/homebrew/bin/gitleaks git --pre-commit --staged
  ```
  `git config --get core.hooksPath` → `githooks` (confirmed set in this local clone's `.git/config`), but nothing in the repo sets this automatically — `package.json`'s only lifecycle script is `"postinstall": "prisma generate"` (no `git config core.hooksPath githooks` step), and neither `README.md` nor `CONTRIBUTING.md` mention `githooks/`, `core.hooksPath`, or gitleaks at all (`grep -n -i "hook\|gitleaks" CONTRIBUTING.md README.md` — the only hits are unrelated React-hooks prose).
- Why it matters: (a) on any machine that isn't Apple Silicon with Homebrew at the default prefix (Intel Mac: `/usr/local/bin`; Linux; gitleaks installed via `go install` or a package manager), the hook fails on every commit with "No such file or directory," blocking all local commits until the contributor either finds and fixes the hook or gives up and commits without it; (b) even where the path is correct, `core.hooksPath` is local-only git config — a fresh clone has it unset, so the "guardrail" silently does nothing until someone manually runs `git config core.hooksPath githooks`, which nothing tells them to do. The project's own `.claude/skills/lwd-security-and-secrets/SKILL.md:245-247` and `:264-265` already flags this exact gap internally, but that knowledge has not made it into human-facing docs.
- Fix: (1) add `git config core.hooksPath githooks` to a `postinstall`/`prepare` script or document it as step 1 in `CONTRIBUTING.md`; (2) make the hook portable — `command -v gitleaks >/dev/null 2>&1 && gitleaks git --pre-commit --staged || echo "gitleaks not found, skipping local scan (CI will still catch it)"` instead of a hardcoded absolute path.

### MEDIUM

**M1. `.env.example` documents 6 env vars that are used nowhere in the codebase (Stripe/PayPal credentials)**
- Severity: Medium
- Evidence: `.env.example:53-61` lists `STRIPE_SECRET_KEY`, `NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY`, `STRIPE_WEBHOOK_SECRET`, `PAYPAL_CLIENT_ID`, `PAYPAL_CLIENT_SECRET` (also echoed in `README.md:181-185`'s "Optional" env table, and `README.md:299-301,325,376` describe wiring webhook endpoints for them). `grep -rn "STRIPE_SECRET_KEY\|PAYPAL_CLIENT_ID\|STRIPE_WEBHOOK_SECRET\|NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY" src` returns **zero matches** anywhere in `src/`. Payment gateway credentials are actually stored per-organization, encrypted in the database via `src/server/services/gateway-config.ts` (19 lines, no `process.env` reference at all), keyed by `GATEWAY_ENCRYPTION_KEY`/`GATEWAY_ENCRYPTION_KEYS`. `src/app/api/webhooks/` only has `inbound-email/`, `resend/`, and `stripe/` subdirectories — there is no `paypal/` webhook route despite `README.md:376` telling a self-hoster to point PayPal at `https://yourdomain.com/api/webhooks/paypal`.
- Why it matters: a new contributor (or self-hoster, per the README's "Self-Hosting Guide") who fills in `STRIPE_SECRET_KEY` in `.env` per the docs will find it does absolutely nothing — real gateway setup happens through the app's own Settings → Payment Gateways UI (`src/components/settings/GatewaySettingsForm.tsx` / `src/server/routers/gatewaySettings.ts`), which the README's env-var-first framing actively obscures. `README.md:376`'s PayPal webhook URL is simply wrong (route doesn't exist).
- Fix: remove the 5 Stripe/PayPal vars from `.env.example` and the README env table, replace with a one-line pointer to Settings → Payment Gateways; fix or remove the `/api/webhooks/paypal` reference in the Self-Hosting Guide.

**M2. `DIRECT_DATABASE_URL` — the var that actually makes `prisma migrate deploy` work against Supabase — is undocumented**
- Severity: Medium
- Evidence: `prisma.config.ts:15`: `url: process.env["DIRECT_DATABASE_URL"] ?? process.env["DATABASE_URL"]`, with an inline comment explaining that Supabase's transaction-pooler URL (port 6543) doesn't support DDL and migrations need the session pooler/direct connection instead. `grep -n "DIRECT" .env.example` returns nothing.
- Why it matters: a fresh setup following only `.env.example` (as `README.md:145-159` instructs) will point `DATABASE_URL` at whatever connection string Supabase's dashboard shows first (often the pooler URL), and `npx prisma migrate deploy`/`migrate dev` will fail or hang with a DDL error the docs give no path out of. This is a known, previously-diagnosed trap (`.claude/skills/lwd-build-and-env/SKILL.md`'s "The DIRECT_DATABASE_URL trap" section) that hasn't been fixed at the source.
- Fix: add `DIRECT_DATABASE_URL` to `.env.example` with the same explanatory comment already in `prisma.config.ts`.

**M3. `npm run db:seed` is a documented no-op — README overstates it**
- Severity: Medium
- Evidence: `README.md:198`: `npm run db:seed      # Seed the database with sample data`. Actual `prisma/seed.ts` (10 lines):
  ```ts
  async function main() {
    console.log("Seeding complete (no global seed data — org-scoped records only).");
  }
  ```
- Why it matters: onboarding says to expect sample data; there is none. A new dev runs the seed, sees a success message, then finds an empty app and has no idea whether that's expected or something broke. Real data only appears after creating an org through the onboarding UI.
- Fix: either implement a minimal seed (one demo org + a few invoices) or rewrite the README line to say seeding is a no-op and real data comes from onboarding.

**M4. Two undocumented, unvalidated env vars (`UPSTASH_REDIS_REST_URL`/`UPSTASH_REDIS_REST_TOKEN`) silently disable edge rate limiting when absent**
- Severity: Medium (borders on security)
- Evidence: `src/lib/rate-limiter.ts:25-26` reads `process.env.UPSTASH_REDIS_REST_URL` / `_TOKEN` directly; neither appears in `.env.example` or `src/lib/env.ts`. Confirmed live via the repo's own re-verification grep (`comm -23` between vars read in `src/` and vars declared in `.env.example`), which also surfaced `GEMINI_MODELS`, `GEMINI_REPLY_TRIAGE_MODELS`, and `OPENAI_MODEL` as further undocumented, unvalidated (Tier-3) config — `GEMINI_REPLY_TRIAGE_MODELS` in particular doesn't appear even in the project's own `.claude/skills/lwd-config-and-flags` inventory, meaning it was added after that doc was last verified (2026-07-05).
- Why it matters: if unset in production, `getRateLimiters()` returns `null` and the edge middleware (`src/proxy.ts`) silently skips rate limiting on every public endpoint — no error, no log, no way to notice short of an incident. Being outside `src/lib/env.ts`'s `createEnv` schema means there's no boot-time validation catching a typo'd var name either.
- Fix: add both to `src/lib/env.ts` as optional server vars with a comment identical in spirit to the `GATEWAY_ENCRYPTION_KEY` production `.refine()` pattern already used there (warn/fail if unset in production), and document all four vars (`UPSTASH_*`, `GEMINI_MODELS`, `GEMINI_REPLY_TRIAGE_MODELS`, `OPENAI_MODEL`) in `.env.example`.

**M5. No `typecheck` npm script — CI's most important gate has no local equivalent**
- Severity: Medium
- Evidence: `package.json` scripts (10 total: `dev`, `build`, `analyze`, `start`, `lint`, `postinstall`, `db:migrate`, `db:seed`, `backfill:payer-tin`, `db:push`, `db:studio`, `test`, `test:run`, `test:coverage`, `test:eval`) contain no `typecheck`/`type-check` entry. CI's `check` job (`.github/workflows/ci.yml`) runs `npx tsc --noEmit` directly, not via an npm script.
- Why it matters: combined with `next.config.ts:49`'s `ignoreBuildErrors: true` and `CONTRIBUTING.md`'s Test-Your-Changes section never mentioning `tsc`, there is no discoverable, documented way for a contributor to run the one check most likely to catch a real bug (see H1) before pushing.
- Fix: `"typecheck": "tsc --noEmit"` in `package.json`; reference it in `CONTRIBUTING.md`'s "Test Your Changes" list.

**M6. `.github/workflows/ci.yml`'s lint step contradicts the repo's own `lwd-validation-and-qa` skill doc**
- Severity: Medium (docs-staleness finding, listed here because it's a concrete, dated, verifiable drift)
- Evidence: `.claude/skills/lwd-validation-and-qa/SKILL.md` (dated "Verified 2026-07-05") states: *"lint | eslint | Disabled — no lint step in `ci.yml`."* Current `.github/workflows/ci.yml` (re-read today) has an explicit, active `Lint` step: `run: npm run lint`, immediately after the `Type check` step, and it is not marked `continue-on-error`.
- Why it matters: this is the single best proof point in the whole audit that "docs describing this codebase get stale within ~2 months, even docs written specifically to survive re-verification." Anyone (human or agent) trusting that skill file's lint claim today would be wrong, and would incorrectly conclude ESLint warnings (see M7) can pile up forever without any CI signal — they can't turn into CI failures, but the step does run and is visible on every PR.
- Fix: re-run the skill's own listed "re-verify with" command block against `ci.yml` and update the stale line; consider a lightweight periodic job (or a pre-commit note) that diffs these skill docs' verified-command output against current reality.

**M7. 68 ESLint warnings (0 errors) accumulate with no ratchet — 26 are `react-hooks/*`**
- Severity: Medium
- Evidence: `npm run lint` (12s wall clock) → `✖ 68 problems (0 errors, 68 warnings)`, exit code 0. Breakdown: `react-hooks/set-state-in-effect` ×23, `@typescript-eslint/no-unused-vars` ×20, `jsx-a11y/alt-text` ×6, `react-hooks/exhaustive-deps` ×2, `@typescript-eslint/no-unused-expressions` ×2, `react-hooks/immutability` ×1, `@next/next/no-location-assign-relative-destination` ×1. `eslint.config.mjs:24-30` deliberately sets these two hooks rules to `"warn"` with a comment explaining they're being "burned down deliberately" rather than bulk-refactored — this is an intentional, documented decision, not an oversight.
- Why it matters: intentional as the *initial* choice may be, there is no `--max-warnings` ceiling or count check anywhere in CI, so the number can silently grow (new violations are free) as easily as shrink — nothing distinguishes "we're paying down 23 warnings" from "we're now at 40."
- Fix: add a warning-count ratchet (a small script comparing current count to a committed baseline, failing CI only if the count increases) rather than gating on zero — keeps the deliberate no-big-refactor policy while preventing silent regrowth.

**M8. Package.json `overrides` block has no documented rationale**
- Severity: Medium
- Evidence: `package.json`'s `overrides`: `@hono/node-server` (pinned `^1.19.13`), `next.postcss` (`^8.5.13`), `resend.svix` (`$svix`, i.e. forced to match root `svix`). JSON permits no comments, and no rationale exists anywhere else in the repo (checked `CONTRIBUTING.md`, `README.md`, `docs/*.md`). Contrast with `.ncurc.yml:1-19`, which documents its two pinned majors (`eslint`, `typescript`) in exemplary detail, including the exact peer-dependency conflict and a commit hash to check before ever removing the pin.
- Why it matters: an override with no rationale is a landmine for the next dependency bump — nobody knows if it's safe to remove, so it either never gets revisited (permanent unnecessary constraint) or gets removed blind (reintroducing whatever bug it fixed).
- Fix: add a short comment block near the `overrides` key's sibling location — e.g. a `# Dependency overrides` section in `CONTRIBUTING.md` — one line per override, same style as `.ncurc.yml`.

**M9. Largest tRPC router (`invoices.ts`, 1,774 lines) is 2× the next-largest and undocumented as a split candidate**
- Severity: Medium
- Evidence: `wc -l src/server/routers/*.ts | sort -rn`: `invoices.ts` 1774, `reports.ts` 974, `portal.ts` 652, `clients.ts` 583, `dashboard.ts` 582 (63 router files total, 14,706 lines). Non-generated, non-test files >800 lines anywhere in `src/`: only 4 — `src/server/routers/invoices.ts` (1774), `src/components/invoices/InvoiceForm.tsx` (982), `src/server/routers/reports.ts` (974), `src/server/services/books-assistant.ts` (958).
- Why it matters: tRPC natively supports merging sub-routers (`t.router({ ... })` composition), so `invoices.ts`'s size is a structural choice, not a framework limitation — at 1,774 lines it's the single highest-friction file in the codebase for review, merge conflicts, and onboarding navigation.
- Fix: split into `invoices/{crud,pdf,payments,reminders}.ts`-style sub-routers merged under the existing `invoices` router key, following the same domain boundaries already visible in `src/components/invoices/`'s ~40 component files.

- Severity: Low (would be higher if a version-sensitive bug were found; none was in this pass — `npm install`, `tsc`, `eslint`, and `vitest` all ran clean on v26)

## What's already good

- **`src/lib/env.ts`'s `@t3-oss/env-nextjs` schema** is thorough (40 validated vars, `.refine()`-based conditional production requirements for `GATEWAY_ENCRYPTION_KEY` and `INNGEST_SIGNING_KEY`) — real, working boot-time validation, not just documentation.
- **CI is comprehensive and fast to reason about**: `tsc --noEmit`, `npm run lint`, `npm run test:coverage`, `npx next build` (placeholder env, no live DB touch), plus separate `codeql.yml`, `gitleaks.yml`, `actionlint` jobs — all with sensible `timeout-minutes`, and a documented, safe Dependabot auto-merge policy (`dependabot-auto-merge.yml`: only patch/minor, majors always manual, with an explicit comment flagging the branch-protection dependency).
- **Dependency pin discipline**: `.ncurc.yml` and `dependabot.yml`'s `ignore:` block are kept in sync (by comment instruction) and both document the exact peer-dependency conflicts (ESLint 10 / TypeScript 7) forcing the pins, with a commit hash reference for historical context.
